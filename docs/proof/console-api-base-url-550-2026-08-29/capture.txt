WHAT THE MODEL ID IS, AND A CORRECTION
--------------------------------------
An earlier version of this log said "hive-default" was the seeded fallback and
that the QA tester's catalog read returned nothing. That was an inference from
the rendered id, not a measurement, and it was wrong. Correcting it here rather
than quietly editing it away, because a reviewer built a finding on it.

Measured directly afterwards, read only, as the same QA tester account:

  GET https://control-hive.scubed.co/api/v1/catalog/models -> HTTP 200
  11 models, including: deepseek-v4-flash, deepseek-v4-pro, hive-auto,
  hive-default, hive-embedding-default, hive-fast, hive-free, hive-medium

So the catalog does answer for a non-admin viewer, and "hive-default" is what
rung 1 of pickQuickstartAlias selects from that list: the first fixed-price
Hive alias that speaks chat. hive-auto sorts ahead of it and is deliberately
skipped, because it is variable-price and takes a credit hold a fresh account
may not cover (issue #1372). The rendered id is the same either way, which is
exactly why the two cases were indistinguishable from the screenshot alone.

The bounded catalog read added after review stands regardless. Its purpose is
not that the read fails, it is that this page is where an operator goes to
revoke a leaked key and must not wait on a lookup whose only consumer is a
string in a snippet.

INSTALLER VERIFICATION (added after review)
-------------------------------------------
The `ecc:code-review` stream found that the new installer prompt wrote the
operator's answer to a shell variable that `setup_env` never persisted, so a
self-hosted operator would have been asked for the gateway base URL, answered
it, and still had the empty line from `.env.example` in their `.env`. That is
the exact defect issue #550 exists to remove, and worse than the state before
this change, because the operator would believe they had answered it.

Fixed by adding the missing `_write_env_var "HIVE_PUBLIC_API_BASE_URL"` call
beside the others, and verified by running `setup_env` for real against a
throwaway HIVE_HOME with the answer supplied non-interactively:

  with the fix:     HIVE_PUBLIC_API_BASE_URL=https://ai.example-bank.internal/v1
                    PASS: the answered value was persisted

  fix removed:      HIVE_PUBLIC_API_BASE_URL=
                    FAIL: the line is present but does not carry the answered value

The second run is the point: the check goes red against the code as it stood
before the fix, so it is measuring something.
