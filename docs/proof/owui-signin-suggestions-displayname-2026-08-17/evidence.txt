Proof for the three chat front end changes (PR #952), captured 2026-08-17.

Every "after" capture is against a stack running this branch's build, not a
description of it. The Supabase project reference is masked as <project> below;
no token, key or password appears in this file or in the images.

HOW THE STACK WAS RUN
---------------------
  cd deploy/docker
  docker compose --env-file ../../.env -p owui3proof --profile chat build open-webui
  docker compose -f docker-compose.yml -f <local-override>.yml \
      --env-file ../../.env -p owui3proof --profile chat \
      up -d --no-deps --force-recreate open-webui

The local override is three lines and is NOT in this repository, because none of
it should ever be deployed:

  ports: 3399:8080                        compose normally fronts this with Caddy
  OAUTH_CLIENT_ID / _SECRET: obvious fakes so the provider is registered and the
                                          outbound redirect is exercised without
                                          minting or mutating anything on the
                                          shared Supabase OAuth client, whose
                                          redirect URI is registered for the demo
                                          box host only
  ENABLE_SIGNUP / ENABLE_INITIAL_ADMIN_SIGNUP: true, long enough to create one
                                          local account, since the shipped
                                          configuration turns signup off and no
                                          local OAuth login is possible

One further local-only change: the vector database DSN was pointed at the
transaction pooler port instead of the session port. The session pool is capped
at 15 clients and is shared with CI and the live demo box (issue #436); the proof
container crash looped on EMAXCONNSESSION until it stopped competing for those
slots. Nothing was reconfigured on the shared project itself.

ITEM 1, THE REDIRECT ITSELF
---------------------------
Navigating to http://localhost:3399/ with no session, no clicks:

  http://localhost:3399/
  -> http://localhost:3399/auth
  -> http://localhost:3399/oauth/oidc/login
  -> https://<project>.supabase.co/auth/v1/oauth/authorize
       ?response_type=code
       &client_id=local-proof-client-not-a-real-credential
       &redirect_uri=http%3A%2F%2Flocalhost%3A3399%2Foauth%2Foidc%2Fcallback
       &scope=openid+email+profile
       &state=...&nonce=...&code_challenge=...&code_challenge_method=S256

  HTTP 400 {"error_code":"oauth_client_not_found","msg":"invalid client_id format"}

The provider rejects the deliberately fake client id, which is the expected end
of this harness. What it proves is the half that changed: the browser leaves the
sign in page for the provider on its own, carrying PKCE, with no intermediate
page and no click. The inbound half of a successful round trip cannot run
locally, because the real OAuth client's redirect URI is registered for the demo
box host.

02-after-loop-guard-explains-and-offers-retry.png
  Returning to /auth immediately after that redirect. This is the failure the
  owner named: a round trip that comes back without a session. The page does NOT
  redirect again. It says "Sign in did not complete", explains that the provider
  sent the visitor back without a session, and the provider button is the manual
  retry. The orphaned divider is gone.

03-after-provider-error.png
  The provider error path, produced by the backend rather than hand written.
  Hitting the callback with a bogus code:

  $ GET http://localhost:3399/oauth/oidc/callback?code=not-a-real-code&state=not-a-real-state
  -> 302 .../auth?error=The+email+or+password+provided+is+incorrect.+...

  (that redirect targets the host in WEBUI_URL, which on this harness is another
  local port, so the screenshot renders the same URL against this build.)
  The banner carries our own wording, deliberately, and not the query parameter:
  a persistent, officially styled panel on the page people type credentials into
  is not the place to reflect a stranger's sentence back at them. The provider's
  own message still appears once in the transient toast, exactly as before.

04-after-signed-out.png
  /auth?signed_out=1, the state a user lands in after signing out. Neutral, not
  an error, and no redirect: without this the provider session, which outlives
  ours and has no end session endpoint, would sign the same person straight back
  in and signing out would be unreachable.

05-after-manual-escape-hatch.png
  /auth?form=1 still renders the manual page unconditionally. The page was not
  removed; it is where every failure above lands.

  And the refresh path that protects a user edited name is untouched:

  This had to be a build-time patch. The image builds only the front end from

  was found by running the built image rather than by reading the diff.

WHAT IS NOT PROVEN HERE
-----------------------
The inbound half of a successful provider round trip, and therefore a real
provisioning run. The first genuine sign in after this deploy will provide that
confirmation. Existing accounts are unchanged by design: the five accounts that
already store an email address as their display name keep it until their owner
edits it, which 08 shows working, or until the owner approves a separate
migration.
