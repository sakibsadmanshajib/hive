## Do-Not-Repeat additions (2026-07-26, Supabase OAuth consent origin)
- "unauthorized request origin" on the OAuth consent flow is a GoTrue (Supabase server-side) rejection, NOT our code. Source: `supabase/auth` `internal/api/oauthserver/authorize.go` `validateRequestOrigin` (called from both `getAuthorizationDetails` and `approveAuthorization`). It reads the browser `Origin` header, allows it when empty, else requires `utilities.IsRedirectURLValid`. That helper (`internal/utilities/request.go`) passes a URL only if scheme+host+port exactly match `site_url`, OR it glob-matches an entry in `uri_allow_list`. Do not go looking for an Origin check in `apps/web-console` again; `app/oauth/consent/page.tsx` + `components/oauth/consent-panel.tsx` are pure clients of the Supabase JS SDK and enforce nothing.
- Glob semantics gotcha: the `Origin` header is a BARE origin with no trailing slash, so an allow-list pattern of `https://host/**` alone does NOT match it. Always register both the bare origin AND the `/**` form for any host that must serve the consent page.
- The consent page host is NOT configurable per client. GoTrue builds it as `site_url + oauth_server_authorization_path` (authorize.go line ~169), one global value for the whole project. So CI and every deployed environment sharing one Supabase project are forced to share one consent origin. Changing `site_url` is the only lever; there is no per-client override to reach for.
- Resolved #271 on 2026-07-26 by setting `site_url=https://console-hive.scubed.co` and `uri_allow_list=https://console-hive.scubed.co,https://console-hive.scubed.co/**,http://localhost:3000,http://localhost:3000/**` via the Management API. The localhost entries are what keep CI working: after the `site_url` move, `http://localhost:3000` is no longer covered by the site_url exact-match branch, so it must be in the allow list or every CI auth redirect breaks. Revert values were `site_url=http://localhost:3000`, `uri_allow_list=""`.
- Management API calls to `api.supabase.com` need a `User-Agent` header (token at `~/.supabase/access-token`); without it they fail. Project ref is derivable from `SUPABASE_URL` in `.env`.
- `scripts/seed-owui-e2e-user.py` was rotation-unsafe until 2026-07-27 (PR #558): it did `DELETE /api_keys` on the shared `owui-e2e-shim` billing account and minted a replacement BEFORE touching any consumer, so a blind run against a live box left that box on a revoked shim key, and the nightly workflow running it on a schedule revoked the demo box's key once a day. Fixed at the root: `--account-slug` puts a long-lived deployment on its own billing account (CI keeps the default `owui-e2e-shim`), revocation of the previous keys is deferred until every configured consumer carries the new value, `--env-file` rewrites `OWUI_SHIM_KEY` in a compose `.env` atomically, and `OWUI_ADMIN_TOKEN` is accepted for the Open WebUI persisted-config push (an OAuth-only OWUI has no password admin, so the old email/password-only sync could never work on a real deployment). Running it against a live box is now the intended path, with `--account-slug <deployment>` plus `--env-file`. Still do NOT run it merely to obtain login credentials: it rotates the fixture user's password too; use GoTrue `PUT /admin/users/{id}` for that.
- A dead `OWUI_SHIM_KEY` is no longer silent: edge-api probes it at startup and every five minutes and logs `owui: ERROR OWUI_SHIM_KEY is unusable: <cause>` with the remedy (`watchOWUIShimKey` in apps/edge-api/cmd/server/main.go). Read that log, not the model picker: an empty picker issues no request at all, and a populated one was never proof the key resolves.
- GoTrue exposes `PUT /auth/v1/admin/oauth/clients/{id}` for OAuth client updates (both `Authorization: Bearer <service-role-key>` and `apikey:` headers required). The demo box's client had a NULL `client_name`, which rendered the consent page as "Let null connect to Hive?" for every new user; set it to "Hive Chat". Any manually minted OAuth client must get a `client_name`, it is customer-visible on the consent screen.
- Consent is granted once per user+client and stored in `auth.oauth_consents`; subsequent logins auto-approve and never render the Approve button. To actually exercise the Approve path in a live test, delete that user's row for the client first, otherwise a passing test silently skips the whole approve code path.
- Demo box and CI share ONE Supabase project whose Supavisor session-mode pool is capped at 15 clients (`pool_size: 15`). The always-on box parks all 15 as idle client backends, so a CI runner gets `FATAL: (EMAXCONNSESSION) max clients reached in session mode` and Open WebUI (which uses that same Postgres as its own app DB) never becomes healthy, failing the nightly at the boot step with every spec skipped. Symptom looks intermittent because whoever claims the slots first wins: the 2026-07-26 08:19 scheduled run passed, the 12:53 dispatch failed on identical code. Diagnose with `select usename, application_name, state, count(*) from pg_stat_activity where backend_type='client backend' group by 1,2,3`. Filed as #436. Candidate fixes: point OWUI at the transaction-mode pooler port 6543 instead of 5432, shrink the box's per-service pools, or split CI onto its own project. Do NOT touch pooler config while sibling agents are mid-verification against the live box.
